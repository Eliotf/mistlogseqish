# QA prompt: M1 chunk 1.3, shared note parser

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked.

## The project

Mistlog is a Logseq-style notes app forked from Mist. It runs on Cloudflare Workers, Durable Objects, TipTap 3 (ProseMirror) and Yjs. Each page is a Yjs document. The editor shows each line as a ProseMirror paragraph of plain markdown-shaped text, where `- ` marks a bullet, a tab character indents, and `TODO`, `DOING` or `DONE` at the start makes a task.

Read these first, in order:

1. `AGENTS.md`: repo rules and product invariants.
2. `PRD.md`: section 6.1 (links by page ID), section 7 (technical approach), and the decision log entries dated 2026-10-22.
3. `docs/technical-architecture.md`: the "Links", "Shared Note Parser" and "Workspace Index" sections.
4. `docs/reviews/1.3-shared-parser-review.md`: the author's own review guide, including design decisions and known limitations.

## The change under review

These files implement a shared parser. Nothing in the app calls them yet; a later server index and the editor will.

- `app/lib/note-ids.ts`: page IDs (random 8-character IDs, and `journal-YYYY-MM-DD`).
- `app/lib/wikilink.ts`: the `wikilink` mark (attribute `pageId`) as a ProseMirror `MarkSpec`.
- `app/lib/note-parser.ts`: `parseLine` and `parseNote`, which extract links, tags, tasks and search text.
- `app/lib/note-lines.ts`: converters from a Yjs `XmlFragment` and from a ProseMirror doc into the parser's input.
- Tests: `tests/unit/lib/note-ids.test.ts`, `note-parser.test.ts`, `note-lines.test.ts`.
- `vitest.config.ts`: raised coverage floors.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, then `npm run typecheck`, `npm run lint`, `npm run test`.
2. **Check the requirements.** Compare the code against PRD 6.1, AGENTS.md invariants 1, 4 and 7, and the decision log entries for 2026-10-22. Flag any mismatch between what the documents say and what the code does.
3. **Try to break it.** Write additional tests in a new file, `tests/unit/lib/note-qa.test.ts`, covering at least:
   - Server/client parity: documents where `linesFromYjs` and `linesFromProseMirror` might disagree. Try empty paragraphs, marks with no attributes, several overlapping marks, emoji and other characters outside the Basic Multilingual Plane, and documents created directly with `Y.XmlText.format` as in `agents/document.ts`.
   - Offsets: marks that start or end inside a surrogate pair, marks past the end of the line, zero-length marks.
   - Tags: Unicode, punctuation, markdown syntax, URLs, email addresses, emoji, very long lines (check for slow regexes).
   - Tasks: lowercase keywords, keywords mid-line, keywords inside code fences of different shapes, bullets without a trailing space.
   - Journal IDs: leap years, century years (2100 is not a leap year), out-of-range months and days, extra characters.
   - Links: invalid or missing `pageId`, duplicate runs, the same page on many lines, links inside code.
   - The y-tiptap round trip: does a `wikilink` mark survive `prosemirrorToYXmlFragment` and back, including next to `criticHighlight` and `criticAddition` marks?
4. **Review the tests themselves.** Find assertions that would still pass if the behaviour broke. Mutation-test a few: change one line of production code, run the tests, put it back. Good candidates are `inclusive: false`, the duplicate-link check, the hash-suffix stripping and the fence toggle.
5. **Check the design** for problems that will hurt the next chunks: the server index (chunks 1.4 and 1.5) and the editor's link UI (chunk 2.5). For example: is anything missing from `ParsedNote` that the index will need? Will `PARSER_VERSION` be easy to forget to bump?

## Rules

- Do not change production code in `app/`, `agents/` or `workers/`. Only add tests, in `tests/unit/lib/note-qa.test.ts`. If a test you write fails because of a real bug, keep it and mark it with `it.fails(...)` and a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run deploy commands or anything against Cloudflare.
- Do not commit or push. Leave your changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations listed in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage).

Then list findings, most severe first. For each:

- **Severity**: high (wrong results or data loss), medium (wrong in an edge case users will hit), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the input, the expected output and the actual output, or the name of the failing test in `note-qa.test.ts`.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
