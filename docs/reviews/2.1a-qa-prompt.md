You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This change is user-facing, so look hard at what a person editing a title would experience.

## The project

Mistlog is a Logseq-style notes app forked from Mist (Cloudflare Workers, Durable Objects, React Router 7, TipTap, Yjs). Each page is a `DocumentAgent` Durable Object holding a Yjs document; a `WorkspaceAgent` holds a derived index. Links point at page IDs, so renaming a page only changes its title.

This change adds:

- page titles stored in the page's Yjs document (`meta.title`)
- an editable title above the editor
- a uniqueness check through `GET /api/title-check`
- a "New page" button

Read these first, in order:

1. `AGENTS.md`: repo rules, product invariants and gotchas.
2. `PRD.md`: features F2 and F5, open question 3, and the decision log entries dated 2026-10-24.
3. `docs/technical-architecture.md`: the "Page Titles" and "Workspace Index" sections.
4. `docs/reviews/2.1a-page-titles-review.md`: the author's review guide, with decisions and known limitations.
5. `docs/prototype/mistlog-demo.html` (open it in a browser): the agreed interaction for titles. Match its behaviour.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Check the requirements.**
   - Titles must be unique across pages and journals, ignoring case.
   - Renaming must never edit linking pages.
   - Browsers must reach the index only through server routes.
   - App code must not import from `agents/`.
   - Every mouse action needs a keyboard path.

   Compare the title behaviour with the prototype and flag differences.
3. **Try to break it.** Add tests in new files: `tests/unit/components/page-title-qa.test.tsx` (jsdom, with a real `Y.Doc`, following the existing test) and `tests/unit/routes/title-check-qa.test.ts`. Explore at least:
   - **Editing sequences:**
     - blur while a check is still in flight, then type again
     - press Enter twice quickly
     - press Esc while a check is in flight
     - another tab changes the title while a check is in flight
     - the component unmounts mid-check
   - **Input:** titles with leading or trailing whitespace, Unicode whitespace (non-breaking space, zero-width space), emoji, right-to-left text, HTML-like text (`<b>x</b>`), and exactly 200 or 201 characters after collapsing.
   - **Paste:** with no selection, with a selection inside the title, rich text, and multi-line text.
   - **Errors:** does an error clear when appropriate? Is it announced (`role="alert"`)? Is it linked with `aria-describedby`?
   - **The route:** missing or duplicated parameters, very long titles, encoded characters, and an index that throws or times out. What does the browser see?
   - **`findByTitle` in the index:** case and Unicode case folding (`İ`, `ß`, accented letters). Does `title_key` (`toLowerCase()`) match how the route and the UI compare titles? Could two titles that look identical both be allowed?
   - **Keyed screen:** read `app/routes/docs.$id.tsx` and `app/lib/useYjsEditor.ts`. Moving from `/docs/aaaaaaaa` to `/docs/bbbbbbbb` must not reuse the Yjs doc or connection. If you can, write a test that proves it; if not, explain how you checked.
4. **Review the tests themselves.** Find assertions that would pass even if the behaviour broke. Mutation-test a few lines of `PageTitle.tsx`, `api.title-check.ts` and `findByTitle`, beyond the ones listed in the review guide. Run the tests, then put each one back.
5. **Check the design** against what comes next:
   - 2.1b readable URLs from titles, with redirects for old slugs
   - 2.1c journal pages
   - 2.5 links that display titles from the index

   Is anything here likely to make those harder, such as where titles are normalised, or the 2-second index lag?

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or anything against a Cloudflare account. Local `npm run dev` is fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (a saved title is wrong or lost, duplicate titles allowed in normal use, another page's content shown, or a security exposure), medium (a confusing or broken experience in a case users will hit), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: steps or input, the expected outcome and the actual outcome, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, real browser behaviour of contenteditable across Safari, Firefox and Chrome.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
