# Review guide: M2 chunk 2.1a, page titles

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. Earlier guides in `docs/reviews/` cover the parser (1.3), the index (1.4) and index reporting (1.5). Find the commit with `git log -- docs/reviews/2.1a-page-titles-review.md`.

## Context in two minutes

Pages need titles for links, autocomplete, search and readable URLs. Links store page IDs (PRD 6.1), so renaming a page is just editing its title; nothing else changes. That is why the old rename chunk (2.7) was merged into this one. This is the first M2 chunk with visible UI:

- an editable title above the editor
- a "New page" button in the header

## Design decisions to validate

1. **The title lives in the Yjs doc** (`meta.title`, owner-approved). It syncs live and conflicts resolve last-writer-wins. `DocumentAgent.reindex` already sends it, so the index fills in titles within about 2 seconds.
2. **Uniqueness is checked against the index before saving, and fails closed.** If the check errors, the rename is refused.
   Known race: the index lags edits by about 2 seconds, so two pages renamed to the same title inside that window could both pass. Accepted for a single user; merge pages (F32) is the eventual fix.
   Uniqueness includes journal titles, so a page cannot be called "Oct 24th, 2026".
3. **Browsers reach the index only through a server route.** `findByTitle` is not exposed directly; the route is where permission checks will go in M4.
4. **Title rules forbid `[[` and `]]`.** Export writes links as `[[Title]]` (F15), so brackets would break them. Single brackets are allowed.
5. **The screen is keyed by page ID** (`<DocumentScreen key={id}>`). `useYjsEditor` creates its `Y.Doc` with `useMemo(…, [])`. Before this change, Mist only ever navigated to a document from the home page. "New page" navigates from one document to another, which would have reused the previous page's Yjs doc and connection. This is untested by unit tests (see limitations); please check the reasoning.
6. **The `meta.title` key is a schema addition**, so `DOC_FORMAT_VERSION` is now 3. Only new documents are stamped (`POST` sets it if absent); existing documents keep their stamp. Nothing reads the version today.
7. **contenteditable `h1`, not `<input>`.** It wraps long titles like the prototype. The DOM is managed by hand, not by React state, so typing is never interrupted by re-renders. Paste is forced to plain text.
8. **"New page" passes `focusTitle` in history state.** Reloading the page re-applies it, so the title gets focus again. That is harmless.

## How to verify

```sh
npm ci
npm run typecheck && npm run lint && npm run test && npm run build
npx vitest run tests/unit/components/page-title.test.tsx tests/unit/components/new-page-button.test.tsx tests/unit/routes/title-check.test.ts tests/unit/lib/page-title.test.ts
```

Expected: 520 tests pass. Coverage is about lines 63.4%, branches 53.6%, functions 57.2%, statements 61.0%.

Manual check in a browser (`npm run dev`):

1. Open a document and type a title. Press Enter.
2. Open the same page in a second tab; the title should appear there.
3. Create a second page with "New page" (the title should be focused).
4. Give it the first page's title in different case. You should see "A page called "…" already exists. The title was not changed."
5. Press Esc mid-edit; the title should revert.

**Checks already run by the author:**

- **Mutation testing** on `PageTitle.tsx`. Each of these broke at least one test:
  - ignoring the uniqueness result
  - letting other tabs overwrite text while typing
  - Esc not cancelling
- **End to end on this machine.** Under `npm run dev`:
  - two pages were created
  - a Node script acting as an editor client synced one page over the agent WebSocket and set `meta.title` to "Project Notes"
  - after 4 seconds the index held the title, `/api/title-check` refused "project notes" for the other page, allowed it for the same page, and allowed a free title
  - `/agents/workspace-agent/default` still returned 404, and the document page rendered the title field

  The script crashed on a message after setting the title (a bug in the throwaway script, not the app); the results above were read afterwards. The script is not committed.

## Review checklist

- [ ] Nothing in `app/` imports from `agents/`. `WORKSPACE_NAME` now comes from `app/shared/constants.ts`.
- [ ] The title check cannot be skipped by the UI path. Note that a client could still write `meta.title` directly over Yjs; acceptable while single-user.
- [ ] The `/api/title-check` loader validates `pageId` before calling the index, and every response is JSON.
- [ ] `PageTitle` never leaves the DOM showing a title that was not saved: refused, invalid or failed checks revert to the stored title.
- [ ] Keying by page ID does not break Mist's existing flows (home page "Start editing", upload, `/new`).
- [ ] Accessibility: the title has a role and label, errors use `role="alert"` and are linked by `aria-describedby`, and every action has a keyboard path (Enter, Esc, Tab).

## Known limitations

- **Readable URLs** come in 2.1b. The header still shows the page ID.
- **Journal pages** come in 2.1c. Titles are pages-only for now.
- **The page-ID key** is not covered by an automated test; rendering `docs.$id.tsx` needs the full editor stack. Manual check: use "New page" from a page with text, and the new page should be empty.
- **Untitled Mist-era pages** show the "Untitled" placeholder. Several can be untitled at once; uniqueness only applies to real titles.
- **Links don't show titles yet.** That is chunk 2.5.

## Questions for the reviewer

1. Is failing closed right? If the index is down, nobody can rename pages.
2. Should the race in decision 2 be closed now, for example by having the index reserve a title atomically? Or is that over-engineering for one user?
3. Is history state the right way to request title focus, or would a `?new=1` query parameter (cleared after use) be clearer?
