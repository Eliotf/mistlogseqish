# QA prompt: M1 chunk 1.5, documents report to the index

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. Concurrency and failure handling are the focus of this change, so think about orderings and interruptions.

## The project

Mistlog is a Logseq-style notes app forked from Mist, running on Cloudflare Workers and Durable Objects. Each page is a `DocumentAgent` Durable Object holding a Yjs document. A separate `WorkspaceAgent` Durable Object holds a derived index (titles, links, tags, tasks, full text). This change makes every document keep its index entry up to date:

- a throttled re-index about 2 seconds after edits
- retries with backoff until the index confirms
- stale retries ignored, using strictly increasing timestamps
- re-index when a document is opened
- registration when a document is created

Read these first, in order:

1. `AGENTS.md`: repo rules, product invariants and gotchas.
2. `PRD.md`: section 7, and the decision log entries dated 2026-10-23.
3. `docs/technical-architecture.md`: "Workspace Index", especially "How it stays correct".
4. `docs/reviews/1.5-index-reporting-review.md`: the author's review guide, with the design, decisions and known limitations.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Check the requirements.** Compare the code with the documents above:
   - indexing failures must never affect editing or sync
   - a slow retry must never overwrite newer content
   - only created documents with valid page IDs are indexed
   - nothing deletes document data from scheduled work or alarms

   Flag any mismatch.
3. **Try to break it.** Add tests in a new file, `tests/integration/agents/document-index-qa.test.ts`. Copy the mocking approach from `document-agent.test.ts`: the mocked `Agent` with `schedule()`, and `getAgentByName` returning a stub over a real `WorkspaceIndex` from `memoryDb`. Explore at least:
   - **Interleavings:**
     - an edit arrives between writing `dirty: false` and the RPC
     - an edit arrives during the RPC, then the RPC fails
     - two `reindex()` calls overlap (simulate a persisted SDK schedule plus a new one after a restart)
     - the acknowledgement arrives after newer edits
   - **Restarts:** construct a new `DocumentAgent` on the same mocked storage at different points, such as after marking dirty but before `reindex`, or after a failed attempt. Is a re-index always eventually scheduled? Which cases depend on someone reconnecting?
   - **Clock:** `Date.now()` standing still, jumping backwards, or jumping far forwards. Can `updatedAt` ever repeat or go backwards for one document? What happens to ordering across a jump forward followed by normal time?
   - **Stale acknowledgements:** the index holds a newer time than the document's `lastSent`, an equal time, or a page from a different source.
   - **Retry backoff:** the delay sequence, reset after success, and behaviour when `retries` in stored state is corrupted (negative, huge, missing).
   - **Index state record:** missing, corrupt JSON, wrong types (for example `dirty: "yes"`), extra fields.
   - **Guards:** a document with no `exists` row, an invalid name, a journal-style name (`journal-2026-10-23`), and a name that is a valid ID but was never created.
   - **Registration:** POST twice, and POST when `registerPage` throws or hangs. Does a hanging `registerPage` block document creation? Is that acceptable?
4. **Review the tests themselves.** Find assertions that would pass even if the behaviour broke. Mutation-test a few by changing one line of `agents/document.ts`, running the tests and putting it back. Look for mutations the author did not try; the review guide lists the ones they did.
5. **Check the design** against what comes next. Chunk 1.6 adds a weekly check and rebuild through the registry. M2 adds page titles (`meta.title` in the Yjs document) and link marks. Is anything here likely to cause drift, duplicate work, or request storms? For example, many documents opening at once after a parser version bump.

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or anything against a Cloudflare account. Local `npm run dev` is fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (lost or stale index data that never recovers, or editing affected), medium (recovers only after a reconnect or the weekly check, or wasted requests at scale), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the sequence of events, the expected outcome and the actual outcome, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, real Agents SDK scheduling and Durable Object RPC on deployed Cloudflare.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
