# Review guide: 1.6, index rebuild

For a senior engineer reviewing this change. Find the commit with `git log -- docs/reviews/1.6-index-rebuild-review.md`.

## What this step does

When the parser changes, the workspace index now re-reads every page by itself, rather than waiting for each page to be opened. The last change of this kind was parser version 2, which brought `LATER`/`NOW`, priorities and block IDs on tasks.

The rebuild also covers registered pages that were never indexed, such as a page created and never written in. It is a prerequisite for the Logseq import, which will index about 900 pages at once.

- **When it runs:** the first time `WorkspaceAgent` is used after it wakes, it counts registered pages that have no index entry or were built by an older parser. If there are any, and no pass is already running, it starts a pass.
- **How it runs:** each step asks the next 10 pages' `DocumentAgent.refreshIndex()` to send their lines again. It saves a cursor, then schedules the next step one second later with `this.schedule()`. The pass ends when nothing is left.
- **Nothing is cleared first.** Search, backlinks, tasks and title claims keep working, and each page's rows are replaced as it reports.
- **Failures:** a page that fails is logged and skipped, and the next pass (the next wake) retries it.
- **Progress:** the Tasks page says "Updating the index: N pages to go" while anything is left.

## Decisions

- **Rebuild without clearing.** The architecture doc said "clear the derived tables, then re-index". Not clearing keeps results visible during the rebuild and removes the need to refuse title claims while it runs, which the doc's "rebuild constraint" would otherwise require. Re-indexing replaces a page's rows anyway, so the result is the same.
- **The weekly content check** (step 4 in the architecture doc) is not built. It catches indexes that drift without a parser change, and it can come later.

## Where to look hardest

1. **Re-entrancy.** `rebuildStep` awaits a `DocumentAgent` RPC, which calls back into `WorkspaceAgent.updatePage`. Durable Object input gates open while an outbound call is awaited, so the callback runs. Please confirm that doesn't deadlock. A local walk-through is the real test; the unit tests use stubs.
2. **The cursor.**
   - The pass walks the registry in ID order after the cursor, so pages registered behind the cursor mid-pass wait for the next pass.
   - If a step throws outside the per-page `try` (for example, the index's SQL fails), the cursor stays set and no next step is scheduled. The rebuild would then stall until the cursor is cleared. A follow-up could clear the cursor when it is found but no step is scheduled.
3. **Cost.** About 900 pages after an import means about 90 steps, one second apart, and about 900 `DocumentAgent` wakes. That's well within the free plan, but please check that each woken document goes back to sleep. `refreshIndex` uses `reindex`, which may schedule a backup reindex; that's fine.
4. **A briefly noisy count.** A brand-new page is registered before its first index update, so it counts as "to refresh" for a second or two. If the index wakes in that moment, a pass simply re-indexes it, which is harmless.

## Known gaps

- There's no weekly content check yet.
- Pages from Mist's era that were never registered are still found only when opened, as before.
- A stalled pass, where a step throws before rescheduling, isn't detected automatically (see above).

## How to verify

```sh
npm run typecheck && npm run lint && npm run test && npm run build
```

What I ran:

- **Checks:** typecheck, lint, test and build all exit 0. There are 1,073 tests.
- **Deliberate breaks:** 9 in total. One break, refreshing a page that was never created, slipped through at first; I tightened that test, and now all 9 are caught.
- **Not walked through in a browser.** The rebuild has no interface beyond the Tasks note, and a local deploy can't easily simulate "after a parser bump". It will run on the live site after the push, because parser version 2 is already deployed and older pages haven't been opened yet. The Tasks page should show the note, then clear it.
