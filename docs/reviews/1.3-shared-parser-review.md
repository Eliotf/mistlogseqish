# Review guide: M1 chunk 1.3, shared note parser

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. Read it alongside the diff (`git log -- app/lib/note-parser.ts` finds the commit).

## Context in two minutes

Mistlog is a Logseq-style notes app forked from Mist (Cloudflare Workers, Durable Objects, TipTap, Yjs). Each page is one `DocumentAgent` Durable Object holding a Yjs document; the editor shows each line as a ProseMirror paragraph of plain markdown-shaped text.

Two product decisions drive this chunk (both in `PRD.md`):

- **Links point to a page ID, never a title** (PRD 6.1). A link is a `wikilink` mark with a `pageId` attribute. Renaming a page must never break or edit links.
- **One shared parser** (AGENTS.md invariant 7). The server-side workspace index (chunks 1.4 and 1.5) and the editor (M2) must extract links, tags and tasks the same way.

This chunk builds that parser and the mark definition. **Nothing calls it yet**: the index (1.4, 1.5) and the editor's link UI (2.5) will. So review it as a library, not a feature.

## Design decisions to validate

Each item says what was chosen, why, and what the alternative was. Push back on any of them.

1. **The parser takes lines with mark ranges, not a Yjs or ProseMirror document.**
   Why: the server holds Yjs, the editor holds ProseMirror, and the parser should not depend on either. Two thin converters feed one pure function.
   Check: `note-lines.test.ts` proves both converters give identical lines, and identical `parseNote` output, for the same document.

2. **Marks in Yjs are read the way y-tiptap writes them.** Formatting attributes on `Y.XmlText`, keyed by mark name, or `name--<8-char hash>` for marks that may overlap. The hash pattern is copied from y-tiptap's `hashedMarkNameRegex` (`node_modules/@tiptap/y-tiptap/dist/y-tiptap.js`, around line 1157).
   Risk: if y-tiptap changes its encoding, `linesFromYjs` drifts. The round-trip tests use y-tiptap itself, so an upgrade that changes encoding should fail them.

3. **The mark is defined as a plain ProseMirror `MarkSpec`, not a TipTap extension.**
   Why: the server imports this module, and the TipTap extension is only needed when the editor creates links (chunk 2.5), which will wrap this spec.
   Check: nothing registers the mark in `app/components/Editor.tsx` yet. That is intentional.

4. **`DOC_FORMAT_VERSION` is not bumped.** Defining a mark changes no stored document. It will be bumped in 2.5, when the editor starts writing the mark. Recorded in the PRD decision log.

5. **Links are counted everywhere, once per page per line.** That includes inside code fences, because a mark is an explicit user action, not text that happens to look like a link. Duplicate runs of one link (split by other marks) are reported once. Invalid marks are skipped silently: missing or malformed `pageId`, or an impossible journal date.

6. **Tag rules** (judgement calls, compared with Logseq):
   - A tag is `#` at the line start or after whitespace, followed by letters, digits, `_`, `-` or `/` (Unicode-aware).
   - Skipped: digits only (`issue #42`), headings (`# Heading`), URL fragments, `C#sharp`, `(#aside)`.
   - Skipped: anything inside inline code, link text or code fences.
   - Logseq's `#[[multi word]]` form is not parsed. In this app `[[` creates an ID link, so that text becomes a link instead.

7. **Task rules.** `TODO`, `DOING` or `DONE` at the start of the line, after tab indentation and an optional `- `. The keyword must be uppercase, followed by a space or the end of the line. No tasks inside code fences.

8. **Indentation is tab characters only.** Spaces are content. This follows the PRD's Logseq file convention. A note pasted with space indentation will not nest.

9. **Code fences** are lines starting with three backticks (after indent and bullet), toggling on and off. An unclosed fence runs to the end of the page.

## How to verify

```sh
npm ci
npm run typecheck && npm run lint && npm run test     # all must pass
npx vitest run tests/unit/lib/note-                    # just this chunk
```

Expected: 389 tests pass. Coverage is about lines 57.5%, branches 47.1%, functions 48.1%, statements 54.8%. The four new modules are at 100% lines.

Suggested spot checks:

- **Mutation check.** Break something and confirm a test fails. For example, change `inclusive: false` in `wikilink.ts`, remove the `seenLinks` de-duplication, or drop the `--hash` stripping in `note-lines.ts`.
- **Round trip.** Read the "keeps its pageId through a ProseMirror -> Yjs -> ProseMirror round trip" and "survives syncing to a second Yjs client" tests in `note-lines.test.ts`. They are the evidence that a link survives storage and sync.
- **Server/client parity.** The "gives the parser the same result on server and client" test.

## Review checklist

- [ ] The parser is pure: no I/O, no globals, deterministic for the same input.
- [ ] No client code imports from `agents/` (AGENTS.md). These modules live in `app/lib/` and import only `yjs`, `@tiptap/pm` types and `~/shared`.
- [ ] Offsets are UTF-16 code units throughout (JavaScript string indices). ProseMirror and Yjs both use them, so ranges line up. Confirm nothing mixes in code-point counting.
- [ ] `blank()` in `note-parser.ts` keeps offsets stable when hiding link text and inline code. Check edge cases: marks past the end of the line, overlapping ranges.
- [ ] Regexes have no catastrophic backtracking on long lines (`TAG_RE`, `INLINE_CODE_RE`).
- [ ] `isWikilinkAttrs` rejects everything that is not a valid page ID.
- [ ] The tests assert behaviour, not implementation details, and would fail if the behaviour broke.
- [ ] Coverage floors were raised, not lowered.

## Known limitations (deliberate, for later chunks)

- **Mist's suggestion marks are not interpreted.** Text marked as a pending deletion (`criticDeletion`) is still parsed, so a task or tag inside a suggested deletion counts. How collaborative features fit the index is open question 1 in the PRD.
- **Only backtick fences.** `~~~` fences and indented code blocks are not detected. Inline code uses a simple single-backtick pattern; double-backtick spans are not handled.
- **Invalid link marks are dropped silently.** They are not reported anywhere. The index chunk may want to log them.
- **The `/docs/:id` route still only accepts 8-character IDs,** so journal IDs are not routable yet. Fixed in chunk 2.1.
- **Mark ranges are not merged** when a source splits one mark into runs. Consumers must not assume one range per link (the parser handles this).

## Questions for the reviewer

1. Are the tag rules right for how you take notes? Two of them differ from Logseq: digit-only tags, and tags after punctuation such as `(#aside)`.
2. Should invalid link marks be reported (for example as a `problems` array) rather than skipped?
3. Is copying y-tiptap's hash pattern acceptable, or should we import it? y-tiptap does not export it today.
