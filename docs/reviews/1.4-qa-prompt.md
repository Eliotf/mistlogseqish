# QA prompt: M1 chunk 1.4, workspace index

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked.

## The project

Mistlog is a Logseq-style notes app forked from Mist, running on Cloudflare Workers and Durable Objects. Each page is a `DocumentAgent` Durable Object holding a Yjs document. This change adds `WorkspaceAgent`: one Durable Object whose SQLite holds a derived index of every page's title, links, tags, tasks and text, for backlinks, autocomplete, search, the Tasks view and the journal feed. Links point at page IDs, never titles.

Read these first, in order:

1. `AGENTS.md`: repo rules and product invariants.
2. `PRD.md`: section 6.1 (links by page ID), section 7 (technical approach and quality gates), and the decision log entries dated 2026-10-22 and 2026-10-23.
3. `docs/technical-architecture.md`: the "Shared Note Parser" and "Workspace Index" sections.
4. `docs/reviews/1.4-workspace-index-review.md`: the author's review guide, with the schema, design decisions and known limitations.

Nothing calls the index yet. Documents will start reporting to it in the next chunk.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Check the requirements.** Compare the code with the documents above. In particular:
   - the registry is never cleared
   - re-indexing is idempotent
   - the index is derived from documents
   - the index is not reachable from browsers
   - every query will need permission filtering later

   Flag any mismatch.
3. **Try to break it.** Write additional tests in a new file, `tests/unit/agents/workspace-index-qa.test.ts`, using `memoryDb` from `tests/helpers/sqlite.ts`. Cover at least:
   - **SQL safety:** page titles and line text containing quotes, semicolons, `--`, NUL characters, very long strings and emoji. Search input built to break FTS5: unbalanced quotes, `NEAR`, `^`, `:`, `-`, column filters, `*` alone, an empty string, whitespace only, and very long input.
   - **`updatePage` atomicity and idempotency:** repeated updates, updates that remove all links or tasks, a page linking to itself, a link to a page that does not exist, two pages with the same title, and a journal ID passed with a misleading title.
   - **Ordering:** `backlinks` by recency, `searchTitles` prefix-first ranking and ties, `tasks` ordering across journals and pages, `journals()` with and without `before`, and its limits.
   - **`ftsQuery`:** confirm it never produces a query FTS5 rejects. Fuzz it with random strings if you can.
   - **Registry:** `registerPage` and `updatePage` in either order, `clearDerived` followed by re-indexing, and paging with `registeredPages(limit, after)`, including IDs that sort oddly (journal IDs against random IDs).
   - **Router:** `isPrivateAgentPath` with encoded paths (`%2F`, `%77orkspace-agent`), trailing slashes, double slashes and query strings. Check how `workers/app.ts` reads the path (`new URL(request.url).pathname`), and whether the Agents SDK router could still reach the agent through a path the check misses. Read `node_modules/agents/dist` to see how `routeAgentRequest` parses paths.
4. **Review the tests themselves.** Find assertions that would still pass if the behaviour broke. Mutation-test a few by changing one line of `agents/workspace-index.ts`, running the tests, then putting it back. Try:
   - removing a `DELETE` in `updatePage`
   - dropping `ESCAPE '\\'`
   - changing `l.source_id != ?`
   - making `clearDerived` include `registry`
5. **Check the design** against the next chunks. Chunk 1.5: documents call `updatePage` after edits settle and retry until acknowledged. Chunk 1.6: a weekly check and rebuild through the registry. Chunk 2.x: the UI uses `backlinks`, `searchTitles`, `search`, `tasks` and `journals`. Is anything missing, or likely to cause drift or races? For example, a retried old update overwriting a newer one.

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or any command against a Cloudflare account. Local commands such as `npm run dev` and Miniflare are fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (wrong results, data loss, security exposure), medium (wrong in an edge case users will hit), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the input, the expected output and the actual output, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, behaviour on deployed Cloudflare as opposed to local runtimes.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
