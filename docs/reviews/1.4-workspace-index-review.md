# Review guide: M1 chunk 1.4, workspace index

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. Read it alongside the diff (`git log -- agents/workspace-index.ts` finds the commit). If you have not read it, start with `docs/reviews/1.3-shared-parser-review.md`; this chunk builds on that parser.

## Context in two minutes

Each Mistlog page is an isolated `DocumentAgent` Durable Object holding a Yjs document. Cross-page features (backlinks, `[[` autocomplete, search, the Tasks view, the journal feed) need one place to query. This chunk adds that place: a `WorkspaceAgent` Durable Object (a single instance named `default` while single-user) whose SQLite holds a derived index.

Design background is in `docs/technical-architecture.md` ("Workspace Index") and `PRD.md` (section 7, and the decision log for 2026-10-22 and 2026-10-23).

**Nothing writes to the index yet.** Chunk 1.5 makes documents report to it, and chunk 1.6 adds the weekly check and rebuild. This deploy creates an empty, unused Durable Object. Review it as a component with a contract, not a feature.

## Schema

| Table | Columns | Notes |
|---|---|---|
| `meta` | `key`, `value` | `schema_version = 1`. Future schema changes migrate on this. |
| `registry` | `page_id`, `created_at` | **Never cleared.** The list a rebuild walks, since Durable Objects cannot be listed. |
| `pages` | `page_id`, `kind`, `title`, `title_key`, `journal_date`, `has_content`, `updated_at`, `parser_version` | Indexes on `title_key` and `journal_date`. |
| `links` | `source_id`, `target_id`, `line`, `content` | PK `(source_id, target_id, line)`; index on `target_id`. `content` is the linking line as `DocLine` JSON, for backlink context. |
| `tags` | `page_id`, `tag_key`, `name`, `line` | Indexes on `page_id`, `tag_key`. |
| `tasks` | `page_id`, `line`, `state`, `indent`, `text` | PK `(page_id, line)`; index on `state`. |
| `pages_fts` | FTS5: `page_id` (unindexed), `title`, `body` | Tokenizer `unicode61 remove_diacritics 2`. |

## Design decisions to validate

1. **The index parses; documents send lines.** `updatePage({ pageId, title, updatedAt, lines })` runs `parseNote` inside the index.
   Why: one place parses on the server and stamps `parser_version`, and backlinks and search need the line text anyway.
   Alternative: documents send parse results. That would duplicate the parser-version logic and still need the line text.

2. **`updatePage` is a full replace in one transaction.** It deletes the page's `links`, `tags`, `tasks` and `pages_fts` rows, upserts `pages`, then inserts new rows. Re-indexing identical content leaves identical rows (tested).
   Check: the rollback test forces a failure part-way with a SQLite trigger and confirms nothing changed.

3. **Kind and journal title are derived from the page ID**, not trusted from the caller. A `journal-YYYY-MM-DD` ID is always a journal titled from its date.

4. **Titles are not unique in the index.** It records what documents say; refusing would cause drift. Uniqueness is enforced at rename time (chunks 2.1 and 2.7).

5. **The index is private.** Two layers: `isPrivateAgentPath` in `workers/app.ts` (404 before the Agents SDK router), and `onRequest` / `onConnect` in the agent. Browser UI will query through server routes, which is where M4 permission checks will go.

6. **FTS input is quoted per word, with the last word as a prefix.** `ftsQuery('smart "notes')` gives `"smart" """notes"*`. Words without a letter or digit are dropped. This avoids FTS5 syntax errors and injection of FTS operators. It does not use SQL string building: every value is a bound parameter.

7. **`searchTitles` uses `LIKE` on a lowercase key, with escaped wildcards.** Prefix matches rank first, then shorter titles. An empty query returns the most recently updated pages.

8. **RPC, not HTTP, between Durable Objects.** `WorkspaceAgent` methods are called on a `DurableObjectStub` (compatibility date 2025-04-04 supports this). The methods are thin `async` wrappers around `WorkspaceIndex`.

9. **Tests use Node's SQLite.** `node:sqlite` is built into Node 22, so there is no new dependency. It is marked experimental and prints a warning. The `memoryDb` transaction helper uses savepoints so nesting behaves like `transactionSync`.

## How to verify

```sh
npm ci
npm run typecheck && npm run lint && npm run test     # all must pass
npm run build                                          # what Workers Builds runs
npx vitest run tests/unit/agents tests/integration/agents/workspace-agent.test.ts
```

Expected: 454 tests pass. Coverage is about lines 59.9%, branches 49.5%, functions 54.3%, statements 57.3%. `agents/workspace-index.ts` and `agents/workspace.ts` are at 100%. After `npm run build`, `build/server/wrangler.json` should list both bindings and migrations `v1` and `v2`.

**Checks already run by the author:**

- **Mutation testing.** Each of these broke at least one test:
  - not deleting old links
  - removing the transaction around `updatePage`
  - not quoting FTS input
- **Cloudflare runtime.** `WorkspaceIndex` was bundled with esbuild and run inside local `workerd` through Miniflare 4.20260205.0 with SQLite-backed Durable Object storage. Schema creation, `updatePage` (twice), backlinks, FTS5 search with accent folding and snippets, hostile FTS input, title search, tasks, journals, `clearDerived` and the registry all behaved as on Node. One difference found: Durable Object SQLite refuses `sqlite_version()`. The index does not use it. The spike script is not committed; ask if you want it.

## Review checklist

- [ ] Every SQL value is a bound parameter. Only table and column names (from fixed lists) are interpolated.
- [ ] `updatePage` cannot leave a page half-indexed.
- [ ] `clearDerived` never touches `registry`, and nothing else deletes from it.
- [ ] `backlinks` excludes self-links, and works for targets that are not indexed yet (links to placeholder pages).
- [ ] Nothing reachable from a browser can call `WorkspaceAgent`. Try `/agents/workspace-agent/default` and case variants against `npm run dev`.
- [ ] The `wrangler.jsonc` migration is append-only and correctly tagged. **Once deployed, it must never be edited or removed.**
- [ ] Return types are plain serialisable objects (Durable Object RPC uses structured clone).
- [ ] Index sizes and query patterns are reasonable for a few thousand pages.

## Known limitations (deliberate, for later chunks)

- **Nothing reports to the index** until chunk 1.5. There is no backfill, by design: existing documents index themselves when opened.
- **No deleted pages.** `pages` has no `deleted` flag yet. Page deletion and unresolved links come with the all-pages list (M5) or earlier if needed.
- **No content hash** for the weekly check. Chunk 1.6 adds it, using `schema_version` to migrate.
- **No permission filtering.** Single user for now. Every query must filter by viewer in M4. A comment at the top of `workspace-index.ts` says so.
- **`workers/app.ts` has no tests.** It never had any; the new branch is one call to the tested `isPrivateAgentPath`.
- **`journals()` returns only days the index knows about.** A journal created before chunk 1.5 appears only after it is next opened.
- **Large documents are sent whole.** Documents are capped at 1 MB by `/new`, well within Durable Object RPC limits, but each update sends the full text.

## Questions for the reviewer

1. Should `updatePage` reject stale updates, where `updatedAt` is older than the stored value? Today the last call wins. Chunk 1.5 sends updates in order per document, but retries could arrive late.
2. Is storing the linking line as JSON in `links.content` acceptable, or should context be fetched from the source document on demand?
3. Is one index Durable Object per workspace enough? A single instance handles every update and query for the workspace. That is fine for one person, but not for heavy multi-user use.
