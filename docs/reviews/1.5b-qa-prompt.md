# QA prompt: index after a pause (revises chunk 1.5)

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This is timer and concurrency code, so think in timelines.

## The project

Mistlog is a Logseq-style notes app on Cloudflare Durable Objects. Each page is a `DocumentAgent`. After edits, a page sends its content to a workspace index (`reindex`), under a per-document lock that renames also take, retrying with backoff on failure.

This change replaces a fixed 2-second throttle with an in-memory timer: reindex 0.3 seconds after the last edit, or at most 2 seconds after the first unindexed edit. A persisted 2-second schedule stays as a backup, and there is no fast timer during retry backoff.

Read first:

1. `AGENTS.md`
2. `docs/technical-architecture.md`, "Workspace Index", "How it stays correct"
3. `docs/reviews/1.5b-index-after-pause-review.md`
4. `docs/reviews/1.5-index-reporting-review.md`, for the original guarantees

## What to do

1. **Run the checks:** `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`. Report exact results.
2. **Try to break it.** Add tests in `tests/integration/agents/pause-qa.test.ts`, copying the setup from `document-agent.test.ts`. Use fake `setTimeout`, `clearTimeout` and `Date`, and advance time explicitly. Explore at least:
   - edits arriving exactly at 300 ms and 2000 ms boundaries
   - a burst that spans a reindex in flight
   - a rename during a burst
   - a failure, then recovery: does the fast timer come back after the first successful retry?
   - the object re-created mid-burst (an eviction): does the backup schedule cover the lost timer?
   - `Date.now()` jumping backwards or forwards mid-burst
   - many documents bursting at once against one index
3. **Check the 1.5 guarantees still hold:**
   - strictly increasing `updatedAt`
   - `dirty` cleared before the RPC
   - edits during a call are sent next
   - retries continue until confirmed
   - index failures never affect editing or sync
4. **Count index calls** for realistic typing (for example 60 words per minute for 5 minutes, with pauses) compared with the old 2-second throttle. Is the increase reasonable?
5. **Review the tests.** Find assertions that would pass if the behaviour broke, and mutation-test lines the review guide does not list. Put each one back afterwards.

## Rules

- Only add test files. Do not change production code. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug.
- Do not lower coverage floors or weaken tests.
- Do not deploy or touch any Cloudflare account. Do not commit or push.
- Do not report style preferences or the review guide's known limitations, unless you think one is worse than claimed. If so, say why.

## Report format

Start with one line: the check results.

Then list findings, most severe first. For each:

- **Severity**: high (lost or stale index data that does not recover, editing affected, or a call storm), medium, or low.
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the timeline of events and the outcome, or the failing test name.
- **Suggested fix**: one or two sentences.

Then "Tests that would not catch a regression", and finally "Not checked".

If you find no real defects, say so plainly. Do not invent findings.
