# Review guide: M1 chunk 1.5, documents report to the index

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. It builds on chunks 1.3 (shared parser) and 1.4 (workspace index); their guides are `docs/reviews/1.3-shared-parser-review.md` and `docs/reviews/1.4-workspace-index-review.md`. Find the commit with `git log -- docs/reviews/1.5-index-reporting-review.md`.

## Context in two minutes

Each page is a `DocumentAgent` Durable Object holding a Yjs document. Chunk 1.4 added `WorkspaceAgent`, an index that cross-page features will query. This chunk makes every document keep its entry in that index up to date:

- within a few seconds of an edit
- retrying until the index confirms
- never letting a slow retry overwrite newer content
- never letting indexing failures affect editing or sync

After this deploys, the live index fills as pages are created and edited. **There is still no UI that reads it**; that is M2.

## How it works

1. **Edit.** The Yjs `update` handler persists state (unchanged), then calls `markForIndex()`:
   - if the document is indexable, it sets `dirty` in the index state
   - if no reindex is pending, it calls `this.schedule(2, "reindex")`

   `markForIndex` catches everything.
2. **`reindex()`.** It clears the pending flag and returns if the document is not dirty. Otherwise it:
   - picks `updatedAt = max(Date.now(), lastSent + 1)`
   - writes `dirty: false, lastSent: updatedAt` **before** calling the index, so edits during the call set `dirty` again
   - calls `WorkspaceAgent.updatePage` over RPC
3. **On success**, it stores the acknowledgement and resets `retries`. If the index said it held something newer (`applied: false`), it marks dirty, raises `lastSent` to the index's time, and schedules again.
4. **On failure**, it sets `dirty`, increments `retries`, logs the error, and schedules a retry after 5 s, 30 s, 120 s, then 600 s repeatedly.
5. **On connect**, it calls `markForIndex()` if there is no acknowledgement, the acknowledgement's parser version is older than `PARSER_VERSION`, or the state is dirty. This is how Mist-era documents enter the index without a backfill.
6. **On POST (create)**, it awaits `registerPage`, catching failures. The first reindex registers the page anyway.

**Index state**, stored as JSON in `doc_state` under the key `index`:

```ts
{ dirty: boolean, lastSent: number, ack: { updatedAt, parserVersion } | null, retries: number }
```

A corrupt record is treated as new.

**Indexable** means created through POST (an `exists` row) and `isPageId(this.name)`. This stops a WebSocket to an arbitrary ID from adding junk to the index.

## Design decisions to validate

1. **Throttle, not debounce** (owner-approved). A debounce never fires during continuous typing. The throttle bounds index lag at about 2 s plus the time of the call.
2. **Ordering through strictly increasing `updatedAt`** (owner-approved). No schema change. It relies on each Durable Object running one instance at a time, which Cloudflare guarantees, and on `lastSent` being persisted.
   Edge case: if `doc_state` were lost while the index kept a newer time, the `applied: false` path recovers by sending again with a later time.
3. **`dirty` is cleared before the RPC, not after.** That way edits during the call are never lost. The cost is that a failed call must set `dirty` again, which it does.
4. **The pending flag is in memory only.** After a restart, a persisted SDK schedule may still exist, and a new edit can schedule a second one. The second `reindex()` finds `dirty: false` and returns. That is harmless, at the cost of an extra wake-up.
5. **Pages send an empty title** until chunk 2.1 (owner-approved). The code reads `meta.title` from the Yjs document if a string is there, so 2.1 only needs to write it.
6. **Registration on create is awaited.** It adds one RPC to document creation. A failure is caught and does not fail creation (tested).
7. **The whole document is sent every time.** That is simple and fine for one person. Documents are capped at 1 MB by `/new`.

## How to verify

```sh
npm ci
npm run typecheck && npm run lint && npm run test && npm run build
npx vitest run tests/integration/agents/document-agent.test.ts
```

Expected: 477 tests pass. Coverage is about lines 61.1%, branches 51.0%, functions 55.2%, statements 58.7%. The new code in `agents/document.ts` is fully covered; the three uncovered lines are pre-existing Mist code.

**Checks already run by the author:**

- **Mutation testing** on `agents/document.ts`. Each change below broke at least one test:
  - not calling `markForIndex` from the update handler
  - non-increasing `updatedAt`
  - not rescheduling after a stale acknowledgement
  - never retrying
  - indexing invalid page IDs
  - not de-duplicating schedules

  The stale-acknowledgement mutation first survived. The test was strengthened to assert that a reindex is scheduled.
- **End to end on this machine.** `npm run dev`, then a page created with `POST /new` containing a `TODO`, a nested `DOING` and a `#localtest` tag. After 6 seconds, the WorkspaceAgent's local SQLite file (`.wrangler/state/v3/do/mist-WorkspaceAgent/*.sqlite`) held:
  - the page in `registry` and `pages`, with `has_content = 1` and `parser_version = 1`
  - both tasks with the correct indent
  - the tag
  - an FTS row matching `e2e*`

  This exercises the real SDK scheduler and Durable Object RPC, which the unit tests mock.

## Review checklist

- [ ] Nothing on the Yjs update path can throw or await. `markForIndex` is synchronous apart from fire-and-forget `schedule()`, with `.catch`.
- [ ] No sequence of edits, failures and restarts leaves `dirty: true` with nothing scheduled forever. Note: `onConnect` re-arms. A document that is never opened again after losing its schedule is the gap; the weekly check (chunk 1.6) closes it.
- [ ] `updatedAt` cannot go backwards for a document.
- [ ] Retry backoff resets after a success and caps at 10 minutes.
- [ ] Unindexable documents (never created, invalid name) never call the index.
- [ ] Old deletion alarms (pre-1.1 documents) still fire harmlessly. `DocumentAgent` still does not override `alarm()`, and the regression test still passes.

## Known limitations

- **No UI yet.** Nothing reads the index until M2.
- **Pages have empty titles in the index** until chunk 2.1.
- **Links are not exercised end to end.** No editor UI creates `wikilink` marks until chunk 2.5. The parser and index handle them (tested in 1.3 and 1.4).
- **The schedule gap in the checklist above** is closed by the weekly check (chunk 1.6).
- **Free-plan quota.** Roughly one index call per 2 seconds of active typing per open document. Check the Cloudflare plan's Durable Object request limits if usage grows.
- **The tests mock the SDK scheduler and RPC.** The local end-to-end run covers the real ones, but it is not automated.

## Questions for the reviewer

1. Is 2 seconds the right throttle? A shorter delay means fresher search at the cost of more calls.
2. Should retries give up after some time, rather than every 10 minutes forever, to cap wasted requests if the index is broken for a long time?
3. Should the end-to-end check be automated, for example a script run in CI with `wrangler dev`? It would need care, because CI must never touch the production account.
