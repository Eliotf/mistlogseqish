# Review guide: M2 chunk 2.1c, journal pages

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. It builds on 1.5 (index reporting), 2.1b (readable URLs) and 2.1d (server-owned titles); their guides are in `docs/reviews/`. Find the commit with `git log -- docs/reviews/2.1c-journal-pages-review.md`.

## Context in two minutes

Mistlog is Logseq-style, so each day has a journal page. A journal is the `DocumentAgent` named `journal-YYYY-MM-DD`; its title is the date. Unlike other pages, journals are never created with a `POST`. A day is "created" the first time someone writes in it, as agreed in the prototype ("Not saved yet. Today's journal is created when you start typing.").

This chunk adds:

- the `/journal/:date` route
- creation on first text
- a read-only date heading
- a "Today" button in the header

The journal feed on `/` is the next chunk, 2.2.

## Design decisions to validate

1. **Created by the first real text** (owner-approved). Opening a day, an empty paragraph, or whitespace does not create it. The check is `linesFromYjs(fragment).some(text.trim())`, run on each update until the journal exists, then skipped thanks to `existsCache`.
2. **Nothing persisted before creation.** The update handler returns early for an uncreated journal, so browsing days writes nothing to Durable Object storage. Tabs still sync, because `onMessage` relays and server-origin changes broadcast before the early return. The first text persists the whole state (tested by reopening with a fresh agent). The cost: if the object is evicted before anyone types, the in-memory empty document is lost, which is harmless.
3. **"Today" is decided in the browser** (owner-approved). The weekday is rendered on the server, where it is time-zone independent. "Today" and the note use `useSyncExternalStore`, with a server snapshot of `false`/`exists`, to avoid hydration mismatches. The `TodayButton` computes the date on click.
4. **Any real date is openable** (owner-approved). Future days exist only once written, which fuzzy-date links will rely on.
5. **Creation is idempotent.** `ON CONFLICT DO NOTHING` keeps the first `createdAt` when two tabs type at once. Registration in the index is idempotent too (tested).
6. **`exists()` is cached.** It is read on every update, so it is cached after the first read. This changed which SQL calls happen during an update. An existing test that made the `exists` read fail, to check that a bookkeeping failure cannot stop saving or syncing, now targets the index-state read instead, because the cached `exists` is never re-read.
7. **The bug found while re-pointing that test.** With the index-state read failing, an **unhandled rejection** appeared. `onConnect` read the index state *before* sending SyncStep1 and SyncStep2, unguarded. A failure there would throw out of `onConnect`, and the new tab would never receive the document. That broke the rule that indexing never affects editing, and it had been there since 1.5. Now `indexOnOpen()` runs after the document is sent and catches everything. There is a regression test.

```sh

npm run typecheck && npm run lint && npm run test && npm run build
npx vitest run tests/integration/agents/document-agent.test.ts tests/unit/routes/page-routes.test.ts tests/unit/components/journal-heading.test.tsx
TZ=Pacific/Auckland npx vitest run tests/unit/components/journal-heading.test.tsx tests/unit/lib/note-ids.test.ts
TZ=America/Los_Angeles npx vitest run tests/unit/components/journal-heading.test.tsx tests/unit/lib/note-ids.test.ts
```

Expected: 658 tests pass, with no unhandled errors. Coverage is about lines 67.1%, branches 57.8%, functions 61.2%, statements 65.0%. The date tests pass in UTC+13 and UTC−7 as well as locally.

**Checks already run by the author:**

- **The real editor on an empty document.** The real TipTap editor with `Collaboration` was mounted in jsdom on an empty `Y.Doc`. It wrote **nothing** on open (0 updates, 0 fragment children), and its first keystroke produced a line with text. The throwaway probe is not committed.
- **End to end on this machine** (`npm run dev`):
  1. `/journal/2026-10-20` before writing returned 200, `exists: false`, and the page showed "Not saved yet".
  2. A Node client writing `meta.title` on an unwritten journal had it reverted, and the day stayed uncreated.
  3. Typing over the Yjs WebSocket created the journal: `exists: true` with `createdAt`, and the note was gone.
  4. `/docs/journal-2026-10-20` returned 302 to `/journal/2026-10-20`.
  5. `/journal/2026-02-30` returned 404.
  6. A rename through the API was refused as a journal.
  7. The index had `journal-2026-10-20` ("Oct 20th, 2026", has content) in `pages` and `registry`. The day that was only opened was in neither.

## Review checklist

- [ ] No path persists or indexes an uncreated journal. Check `POST`, `onConnect`, `rename` (refused), the revert, and `reindex` (`isIndexable` requires `exists`).
- [ ] `createJournalIfWritten` cannot throw out of the update handler, and its nested `meta.set("version")` transaction behaves correctly. The tests show it does, but check the reasoning.
- [ ] Browser-origin updates are still not broadcast by the handler (they are relayed by `onMessage`), and server-origin ones still are, before the early return.
- [ ] `onConnect` sends the document before any index work, and nothing on that path can throw.
- [ ] The `/journal/:date` loader validates before calling any agent.
- [ ] No hydration mismatch: the server renders the weekday and `exists`-based note; the browser adds "Today".

## Known limitations

- **No journal feed yet;** that is chunk 2.2. `/` is still Mist's landing page.
- **Days written before this chunk.** There were none, because journals could not be opened before.
- **A journal emptied after creation stays created.** The index marks it `has_content: 0`, and the feed (2.2) will skip it.
- **`existsCache` is per object instance.** Nothing deletes `exists`, so it cannot go stale.

## Questions for the reviewer

1. Should future journals beyond some horizon (for example 10 years) be refused, to stop accidental far-future dates?
2. Is skipping persistence before creation worth its subtlety, or would persisting empty days and filtering them out be simpler to reason about?
