# QA prompt: M2 chunk 2.3, bullets and indenting

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This is editor behaviour, so think like someone taking notes quickly: odd caret positions, selections, undo, other people editing, and other input methods.

## The project

Mistlog is a Logseq-style notes app forked from Mist (TipTap, ProseMirror, Yjs). Each line is one paragraph of raw markdown text. A bullet is `- ` after leading tab characters, and that text format must stay Logseq-compatible.

This change adds:

- Tab and Shift+Tab to indent and outdent with children
- Enter to continue bullets
- Backspace after `- ` to outdent or remove the bullet
- bullets drawn as dots with indentation guides

In suggest mode the keys do nothing special.

Read first:

1. `AGENTS.md`, especially invariant 4 and the gotchas
2. `PRD.md`: F7 and F34, and the decision log entries dated 2026-10-27
3. `docs/technical-architecture.md`: "Bullets and Indentation"
4. `docs/reviews/2.3-bullets-review.md`: includes a behaviour table
5. `docs/prototype/mistlog-demo.html` (open it in a browser): the agreed behaviour

## What to do

1. **Run the checks:** `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`. Report exact results.
2. **Check the requirements.** The stored text must only ever contain tabs (never spaces) for indentation, and `- ` for bullets. No key may lose text or marks. Compare with the prototype.
3. **Try to break the pure logic.** Add property-style tests in `tests/unit/lib/bullets-qa.test.ts`. For random line lists and positions, check that:
   - applying any plan never changes text after each line's prefix
   - indentation never exceeds the previous line's plus one
   - children always move with their parent
   - indenting then outdenting the same lines restores the original text, when indenting was allowed

   Also try:
   - bare `-`
   - `-` followed by several spaces
   - lines that are only tabs
   - mixed tabs and spaces
   - task lines (`- TODO x`)
   - code fences
4. **Try to break the editor.** Add tests in `tests/unit/lib/bullet-editing-qa.test.ts`, copying the setup in `bullet-editing.test.ts`: the real TipTap editor with `Collaboration`, keys delivered through `handleKeyDown`. Explore at least:
   - selections spanning partial lines, a selection ending at the start of a line, and select-all
   - Tab on the first line
   - Enter at every caret position in `\t- TODO **bold** text`
   - Enter on a line whose children are separated by an empty line
   - Backspace at the start of a plain line after a bullet
   - undo and redo of every key
   - two Yjs clients:
     - indenting the same line at once
     - one indenting while the other types at the start of the line
     - one pressing Enter while the other deletes the line
   - suggest mode with suggestion marks present
   - marks spanning the split point
5. **If you can run a real browser** (for example headless Chrome against `npm run dev`; see the gotcha about Vite's first-load reload), check:
   - caret and selection behaviour around the drawn dots
   - Home and End
   - Shift+arrow selections
   - copy and paste of indented bullets: what text lands on the clipboard?
   - IME composition in Chinese or Japanese (Enter during composition)
   - screen reader output for bullets
6. **Review the tests.** Find assertions that would pass if the behaviour broke. Mutation-test lines of `bullets.ts` and `bullet-editing.ts` beyond those listed in the review guide, then put each one back.

## Rules

- Only add test files. Do not change production code. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug.
- Do not lower coverage floors or weaken tests.
- Do not deploy or touch any Cloudflare account. Do not commit or push.
- Do not report style preferences or the review guide's known limitations, unless you think one is worse than claimed. If so, say why.

## Report format

Start with one line: the check results.

Then list findings, most severe first. For each:

- **Severity**: high (lost text or marks, non-Logseq text such as space indentation, a corrupt structure after concurrent edits, or the caret leaving the editor), medium (a surprising result users will hit), or low.
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the starting lines and caret, the key, the expected text and the actual text, or the failing test name.
- **Suggested fix**: one or two sentences.

Then "Tests that would not catch a regression", and finally "Not checked".

If you find no real defects, say so plainly. Do not invent findings.
