Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This change splits a rename across the server, the index, the Yjs document and the browser address, so look hard at orderings and partial failures.

## The project

Mistlog is a Logseq-style notes app forked from Mist (Cloudflare Workers, Durable Objects, React Router 7, Yjs). Each page is a `DocumentAgent` Durable Object with a Yjs document; the page title is `meta.title`. A `WorkspaceAgent` holds a derived index, including page titles and readable-URL slugs.

Renaming now works like this:

1. `POST /api/rename` claims the title in the index atomically and returns the new address.
2. The browser saves `meta.title` and moves to the new address.
3. The document re-indexes immediately when its title changes.

Read these first, in order:

1. `AGENTS.md`: repo rules, invariants and gotchas.
2. `PRD.md`: F2, F5, and the decision log entries dated 2026-10-24 and 2026-10-25.
3. `docs/technical-architecture.md`: the "Page Titles", "Readable URLs" and "Workspace Index" sections.
4. `docs/reviews/2.1d-instant-renames-review.md`: the author's review guide, with the rename sequence, decisions and known limitations.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Check the requirements.**
   - Titles must be unique across pages and journals, ignoring case.
   - The document must remain the source of truth.
   - Indexing failures must never affect editing.
   - Browsers must reach the index only through server routes.
   - Old addresses must keep working.

   Flag any mismatch.
3. **Try to break it.** Add tests in new files: `tests/unit/agents/claim-qa.test.ts` (use `memoryDb`), `tests/unit/routes/rename-qa.test.ts`, and `tests/integration/agents/document-rename-qa.test.ts` (copy the mocking approach from `document-agent.test.ts`). Explore at least:
   - **Interleavings, in every order:**
     - claim, then a stale reindex with the old title, then the new reindex
     - claim, then the client never saves `meta.title`, then a later edit reindex
     - two pages claiming the same title back to back
     - page A claims, then page B claims A's old title before A's document saves
     - claiming the title a page already has, in different case
   - **Partial failure:**
     - `claimTitle` succeeds but `meta.title` never syncs: where does the browser end up?
     - the rename request times out after the claim succeeded
     - the index is down during a rename
     - `reindexNow` is called while a scheduled reindex is pending, or while one is in flight
   - **The route:**
     - missing or extra fields, very long titles, titles that normalise to empty
     - `Content-Type` variants (`application/json; charset=utf-8`, uppercase, `text/json`)
     - a huge body, a body that isn't an object (`[]`, `"x"`, `null`)
     - GET, HEAD and OPTIONS
     - how the route behaves when `claimTitle` throws
   - **The observer:**
     - title set to the same value
     - title deleted (`meta.delete("title")`)
     - a non-string title
     - several title changes in one Yjs transaction
     - title changes arriving during document creation (`POST`)
     - changes to other `meta` keys (`version`)
   - **Uniqueness bypass:** confirm and describe what happens when a client writes `meta.title` over Yjs without calling `/api/rename`. Can that produce two pages with the same `title_key` in the index? What would the user see?
4. **Review the tests themselves.** Find assertions that would pass even if the behaviour broke. Mutation-test a few lines of `claimTitle`, `reindexNow`, `api.rename.ts` and `PageTitle`'s commit, beyond those listed in the review guide. Run the tests, then put each one back.
5. **Check the design** against what comes next:
   - 2.1c journal pages
   - 2.5 links displaying titles from the index
   - search and backlinks, which will want faster indexing of typing
   - multi-user sharing in M4, where concurrent renames by different people become realistic

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or anything against a Cloudflare account. Local `npm run dev` is fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (duplicate titles in normal use, a lost title, the browser left on an address that doesn't resolve, editing affected, or a security exposure), medium (a wrong or confusing state that self-heals only after a later edit or reload), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the sequence of events, the expected outcome and the actual outcome, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, real browser navigation timing, or deployed Durable Object RPC latency.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
