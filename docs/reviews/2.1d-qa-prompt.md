# QA prompt: M2 chunk 2.1d, instant renames and server-owned titles

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This change is about **concurrency and a single-writer guarantee**, so think in orderings, interleavings and partial failures, not just inputs.

## The project

Mistlog is a Logseq-style notes app forked from Mist (Cloudflare Workers, Durable Objects, React Router 7, Yjs). Each page is a `DocumentAgent` Durable Object with a Yjs document; the page title is `meta.title`. A `WorkspaceAgent` holds a derived index, including titles (which must be unique across pages and journals, ignoring case) and readable-URL slugs.

The design under review, in short:

- Only `DocumentAgent.rename` writes `meta.title`. It does so after the index claims the title, while holding a per-document lock that reindexing also takes.
- Title writes from browsers are reverted.
- Journal-date titles are reserved.
- Titles are normalised to NFC with invisible characters removed.

Read these first, in order:

1. `AGENTS.md`: repo rules, invariants and gotchas, especially titles.
2. `PRD.md`: F2, F5, and the decision log entries dated 2026-10-24 to 2026-10-26.
3. `docs/technical-architecture.md`: the "Page Titles", "Readable URLs" and "Workspace Index" sections.
4. `docs/reviews/2.1d-instant-renames-review.md`: the author's review guide, with the problems found, the rename sequence, decisions and the residual risk.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Try to break the single-writer guarantee.** Find any way, by a browser or by server code paths, that `meta.title` can change without `DocumentAgent.rename`, or that the index's title for a page can differ from its document's for longer than one reindex. Look at:
   - `POST` document creation, which seeds content
   - `onConnect` sync steps: SyncStep2 from the client contains the client's whole state. If a stale client with a different `meta.title` connects, what happens?
   - offline clients reconnecting with queued title writes
   - Yjs `UndoManager` scope
   - `meta.delete("title")`
   - non-string titles
   - several key changes in one transaction
3. **Try to break uniqueness.** Write tests in `tests/integration/agents/rename-qa.test.ts`. Copy the mocking approach from `document-agent.test.ts`: the mocked `Agent` with `schedule()`, and `getAgentByName` returning a stub over a real `WorkspaceIndex` from `memoryDb`. Use several `DocumentAgent` instances sharing one index, and promise gates to control timing. Explore at least:
   - two pages renaming to the same title with every interleaving of claim, write and reindex
   - page A renaming while a reindex of A is in flight, with page B claiming A's old and new titles at each step
   - a rename while a retry with backoff is pending
   - the index failing between the claim and the reindex
   - a rename when the index has just been cleared (`clearDerived`), simulating the 1.6 rebuild constraint: show what goes wrong today if a claim happens mid-rebuild
4. **Check the lock.**
   - Can it deadlock? For example, if `reindex` awaits something that waits for a rename.
   - Can an exception leave it permanently held?
   - Can work starve: a rename stuck behind a slow reindex with a long retry?
   - Does serialising `reindex` change any 1.5 guarantee, such as the throttle, retries, or `dirty` handling?
5. **Check the broadcast.**
   - Server-origin updates are sent to every connection. Can that echo or loop with `onMessage` relays?
   - Do browsers receive reverts and renames exactly once?
   - What happens to awareness?
6. **Check inputs.** `normalizeTitle` with every invisible or format character you can think of (Unicode category Cf), Unicode case folding against `toLowerCase` (`İ`, `ß`, final sigma), and NFC against NFKC look-alikes (full-width letters, ligatures). Can two titles that look identical both pass? Is that serious for a single user?
7. **Review the tests.** Find assertions that would pass even if the behaviour broke. Mutation-test lines the author did not list in the review guide. Run the tests, then put each one back.

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or anything against a Cloudflare account. Local `npm run dev` is fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (duplicate titles in normal use, a title change that bypasses rename, a lost or reverted user rename, a deadlock, or editing affected), medium (a wrong state that self-heals only after a later edit or reload, or wasted requests at scale), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: the sequence of events, the expected outcome and the actual outcome, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, Durable Object RPC ordering guarantees on deployed Cloudflare.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
