# Review guide: index after a pause (revises M1 chunk 1.5)

For a senior engineer reviewing this change. It replaces the 2-second reindex throttle from chunk 1.5 with "index soon after a pause". Read `docs/reviews/1.5-index-reporting-review.md` for the original design, and `docs/reviews/2.1d-instant-renames-review.md` for the index lock this relies on. Find the commit with `git log -- docs/reviews/1.5b-index-after-pause-review.md`.

## Why

Search, backlinks, the Tasks view and the journal feed's list of days all read the workspace index. With a 2-second throttle, they lagged typing by up to 2 seconds. The owner asked for faster indexing before building the journal feed (2.2).

## What changed

| File | What it does |
|---|---|
| `agents/document.ts` | `INDEX_PAUSE_MS` (300) and `INDEX_MAX_WAIT_MS` (2000). `armPauseTimer()`, called from `markForIndex` unless the document is in retry backoff, reindexes 300 ms after the last edit, or 2000 ms after the first unindexed edit, whichever is sooner. A failed reindex cancels any pending pause timer. The persisted `schedule("reindex")` at 2 s (`INDEX_DELAY_SECONDS`) is unchanged and is now the backup. |
| `tests/integration/agents/document-agent.test.ts` | The file now uses fake `setTimeout` and `clearTimeout`, so in-memory timers fire only when a test advances time and cannot leak into the next test. 6 new tests in "indexing after a pause" (which also fake `Date`). |
| `PRD.md`, `docs/technical-architecture.md` | The decision superseding the throttle, and the updated "How it stays correct". |

## Design decisions to validate

1. **Debounce with a maximum wait** (owner-approved). Pausing indexes within 0.3 seconds; continuous typing still indexes at least every 2 seconds.
2. **The in-memory timer plus the persisted backup.** `setTimeout` is lost if Cloudflare evicts the object between messages. The 2-second SDK schedule survives eviction. Both call `reindex()` under the index lock, so they cannot overlap each other or a rename. Whichever runs second finds `dirty: false` and makes no RPC.
3. **No fast timer during backoff.** If the index is failing (`retries > 0`), edits do not arm the timer, and a failure cancels a pending one. Otherwise every pause in typing would hit a down index, defeating the 5 s, 30 s, 2 min and 10 min backoff. This was found by a test: an edit made before a failure had already armed the timer, causing one extra attempt.
4. **Cost.** Index calls rise from about one per 2 s of typing to about one per pause, capped at one per 2 s while typing continuously. For one person that is a modest increase. Check it against the Cloudflare plan's Durable Object request limits if usage grows.

## How to verify

```sh
npm run typecheck && npm run lint && npm run test && npm run build
npx vitest run tests/integration/agents/document-agent.test.ts -t "indexing after a pause"
```

Expected: 664 tests pass.

**Checks already run by the author:**

- **Mutation testing.** Each of these broke at least one test:
  - removing the 2-second maximum wait
  - arming the fast timer during backoff
  - keeping a pending timer after a failure
  - edits not restarting the pause
- **End to end on this machine** (`npm run dev`): text typed over the Yjs WebSocket became searchable in the local index after about 520 ms, measured from starting the client script, which itself takes about 250 ms. So the index was about 0.3 s behind, previously about 2 s.

## Review checklist

- [ ] The timer callback cannot throw out of a `setTimeout`: `reindex()` is caught.
- [ ] No path leaves a timer armed for a document that is not indexable.
- [ ] The burst start resets correctly: a new burst starts only when no timer is pending.
- [ ] Fake timers in the test file do not hide a real-timer problem. Tests that need `Date` fake it explicitly.

## Known limitations

- **`Date.now()` drives the maximum wait,** so a clock jump could shorten or lengthen one burst. That is harmless.
- **Typing in many documents at once multiplies index calls.** That is fine for one person.
