# Review guide: M2 chunk 2.1d, instant renames and server-owned titles

For a senior engineer reviewing this change. It explains what was built, why each choice was made, how to verify it, and where the risks are. It revises parts of 2.1a (titles) and 2.1b (readable URLs); read `docs/reviews/2.1a-page-titles-review.md` and `docs/reviews/2.1b-readable-urls-review.md` first.

This chunk is **two commits**, reviewed together:

- `feat: make renames instant`: renames through the server and an immediate reindex on title change.
- `fix: make the server the only writer of page titles`: the result of an architecture review of the first commit, before either was pushed.

Find them with `git log -- docs/reviews/2.1d-instant-renames-review.md`.

## Context in two minutes

After 2.1a and 2.1b, a rename reached the workspace index on the 2-second reindex throttle. The browser address updated only on the next load, and the uniqueness check could race.

The owner asked for faster renames. The first commit made renames go through `POST /api/rename`, which claimed the title in the index and returned the new address.

Before pushing, the owner asked for a review of every path that can change a title. It found that uniqueness was enforced on the **index's copy** of the title while the **original** (`meta.title` in each document) could still be written by any browser, and changed by reindexes the claim did not coordinate with. The second commit fixes that by giving titles exactly one writer.

## Problems the review found

| # | Problem | Fixed by |
|---|---|---|
| 1 | A reindex carrying page A's old title, in flight when A is renamed, lands after the claim. A looks like its old title, so page B can take A's new one, leaving duplicate titles. | The per-document index lock: a rename claims only after any in-flight reindex has finished. |
| 2 | Any browser (including a stale tab on old code) could write `meta.title` directly, bypassing uniqueness. | `DocumentAgent` reverts title writes from browsers; only `DocumentAgent.rename` writes it. |
| 3 | `/api/rename` accepted any well-formed ID, so it could register and claim titles for pages that never existed. | `DocumentAgent.rename` refuses documents that were never created. |
| 4 | A page could take a future journal's title ("Oct 30th, 2026") before that journal was indexed. | `claimTitle` reserves every journal-date title (`isJournalTitle`). |
| 5 | Titles that look identical (composed or decomposed accents, zero-width characters) could both pass. | `normalizeTitle` stores NFC and strips invisible characters; `titleKey` compares NFC-lowercase. |
| 6 | Claim succeeded but the browser never saved the title (tab closed), leaving the index and document disagreeing; problem 1 could happen in that window. | The server writes `meta.title` in the same step as the claim. |
| 7 | A future rebuild (1.6) would let claims run against a half-rebuilt index. | Recorded as a constraint in the architecture doc and PRD. |
| 8 | Two tabs editing the same title: the last one wins silently. | Accepted; normal for concurrent edits. |

## Rename sequence

1. `PageTitle` POSTs `{ pageId, title }` to `/api/rename`.
2. The route calls `DocumentAgent.rename(title)` on that page's Durable Object.
3. `rename` refuses journals, missing documents and invalid titles, then queues on the **index lock**. Any reindex already in flight finishes first.
4. Under the lock, it calls `WorkspaceAgent.claimTitle`, which runs in one transaction (refuse taken or journal-date titles, record the title, assign the slug).
5. On success it writes `meta.title` with `SERVER_ORIGIN`. The update handler persists it and broadcasts it to every browser, and the observer re-indexes at once (queued behind the lock).
6. The route returns `{ ok, title, path }`, and the browser navigates, with replace, to `path`.

A browser writing `meta.title` itself instead goes through `onMessage`, with origin `CLIENT_ORIGIN`. The observer sets the approved title back with `SERVER_ORIGIN`, and the revert is broadcast to everyone.

## Design decisions to validate

1. **Single writer** (owner-approved). Uniqueness is a cross-page rule, so the writer must check the index first, and there must be only one. The cost is that the server must now broadcast its own Yjs changes. Check that `broadcastUpdate` cannot echo-loop: browser-origin updates are relayed by `onMessage` and skipped by the handler.
2. **Per-document lock, not index-side versioning.** The alternative was a `title_version` on each page, with the index ignoring older titles. The lock is simpler and needs no schema change. It works because a reindex's RPC has *completed*, and so has been processed by the index, before the claim is sent. Please check that reasoning.
3. **The lock covers `reindex` too.** Two reindexes no longer overlap. A retry scheduled from inside a locked reindex just queues. Because `reindex()` starts its work one microtask later, edits made just before a reindex runs go out in that reindex.
4. **The revert keeps the last approved title in memory.** `approvedTitle` is loaded from the persisted `meta.title` when the object starts, and updated on every server-origin change. Titles written by 2.1a clients, before this change, are accepted as approved.
5. **`rename` throws if the index is unreachable.** The route returns 503, the title is unchanged, and the lock is released (tested).
6. **Journal-date titles are reserved for any ordinal suffix** ("Oct 26st, 2026" included), because the intent is clearly a date.
7. **Residual risk.** `meta.title` is written in the same synchronous continuation that `claimTitle` returns in. A process death exactly between them would leave the index ahead of the document until the next reindex reverts it.

## How to verify

```sh
npm ci
npm run typecheck && npm run lint && npm run test && npm run build
npx vitest run tests/integration/agents/document-agent.test.ts tests/unit/routes/rename.test.ts tests/unit/agents/workspace-index.test.ts tests/unit/lib/page-title.test.ts tests/unit/lib/note-ids.test.ts
```

Expected: 627 tests pass. Coverage is about lines 66.3%, branches 57.1%, functions 59.3%, statements 64.1%.

**Checks already run by the author:**

- **Mutation testing**, each change breaking at least one test:
  - rename without the lock: the race test, and only the race test, fails
  - browser title writes not reverted
  - server changes not broadcast
  - browser updates not tagged with their origin
  - renaming a never-created page
  - journal titles not reserved
  - no NFC or invisible-character stripping

  (The first attempt at the lock mutation was invalid, because it left the function uncalled. It was redone so that only the lock was removed.)
- **End to end on this machine** (`npm run dev`):
  1. A rename returned `/page/server-owned`, which answered 200 immediately.
  2. A Node client writing `meta.title` directly over the Yjs WebSocket saw it reverted to "Server Owned". The sneaky slug was 404 and the real one 200.
  3. Renaming a never-created ID: 404, and nothing in the registry.
  4. "Dec 25th, 2026": refused as a journal title.
  5. A decomposed "Café Club" was stored as NFC, and a typed "Café Club" was then refused as a duplicate.
  6. Two pages renamed to the same title concurrently: exactly one succeeded.

  The local index still showed a stale title on one test page, left by a `curl`-only claim made under the first commit's design. That state cannot arise under the final design, and the next reindex of that page reverts it.

## Review checklist

- [ ] Every path that sets `meta.title` goes through `DocumentAgent.rename` (`grep -rn '"title"' agents app`).
- [ ] No sequence of reindexes, renames, retries and failures can leave two pages with the same `title_key`. Consider whether the index's own rebuild in 1.6 respects the constraint.
- [ ] The lock cannot deadlock: `rename` does not await `reindexNow`, and nothing awaits the lock while holding it.
- [ ] The revert cannot loop: it uses `SERVER_ORIGIN`, which the observer treats as approved.
- [ ] Old clients still running 2.1a code (which write `meta.title` locally) see their change reverted and do not break.
- [ ] The rename route validates everything before calling the agent. Errors never leak details.

## Known limitations

- **Typing is still throttled at 2 seconds** for search, backlinks and tasks (owner-approved, to revisit).
- **No automated test covers the navigation in `DocumentLayout`;** the manual check above covers it.
- **`approvedTitle` trusts titles written before this change.** Any duplicates created by the old design remain, and on the live site there were none.
- **Two tabs editing the title at once:** the last one wins.

## Questions for the reviewer

1. Is the lock reasoning in decision 2 sound under Durable Object RPC semantics? Is "the RPC returned" a strong enough guarantee that the index has processed it?
2. Should the server also refuse other `meta` keys from browsers (for example `version`), or only `title`?
