# QA prompt: 2.5d, the side panel

Paste everything below the line into a coding model that has access to this repository, opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Find real defects; do not restate the code.

The change adds a Roam-style side panel. Cmd/Ctrl+click on a link, or Alt+Shift+Enter, opens the page there as a live editor. `t r` toggles the panel, and it is remembered per browser.

The worst outcomes are:

- lost edits
- runaway connections
- shortcuts firing while typing
- the app failing to render (hydration errors)

Read first: `AGENTS.md`, `PRD.md` F18 and the 2026-10-29 decisions, `docs/technical-architecture.md` "Side panel", and `docs/reviews/2.5d-side-panel-review.md`.

## What to do

1. **Run the checks:** `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`. Report each exit code.
2. **Add tests in `tests/unit/lib/side-panel-qa.test.tsx`.** Explore:
   - opening the 11th page
   - reopening a page
   - closing the last page
   - storage holding non-string IDs or a huge list
   - two providers (two tabs) sharing `localStorage`
   - `t r` with IME composition, inside a `[contenteditable]` parent, or with Shift held
3. **Read `app/root.tsx`, `SidePanel.tsx` and `docs.$id.tsx`.**
   - Can server and client render differently (hydration)?
   - Does the panel stay correct when navigating between pages, journals and the feed?
   - Does the same page in the main view and the panel cause problems for comments or presence?
4. **Connections.** Each panel page uses `useYjsEditor`. Check the cap really bounds WebSockets, and that closing a page closes its socket.
5. **If you can run headless Chrome against `npm run dev`:**
   - Cmd+click, Alt+Shift+Enter, `t r`, Comments and ✕.
   - Reload.
   - Phone width.
   - Type in the same page in both views and check it syncs.
   - Count document WebSockets with 10 pages open.

## Rules

- Only add test files. Revert any temporary changes and leave no diff.
- If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)`, and add a comment explaining the bug.
- Do not lower coverage floors or weaken tests.
- Do not deploy or touch any Cloudflare account. Do not commit or push.

## Report format

Start with one line: the check results, with exit codes.

Then list findings, most severe first. For each:

- **Severity**: high, medium, or low.
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**.
- **Suggested fix**.

Then "Not checked". If you find no real defects, say so plainly.
