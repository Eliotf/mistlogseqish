# QA prompt: 2.5a, showing links

Paste everything below the line into a coding model that has access to this repository, opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Find real defects; do not restate the code.

The change makes links display in the editor: links are `wikilink` marks on a stored copy of a title, and the editor shows the target's current title instead. It also refuses browser tabs running older code, because those would delete link text.

The two worst outcomes are lost or corrupted text, and a tab or Durable Object that keeps reconnecting or waking. Treat both as high severity.

Read first:

1. `AGENTS.md`, especially the invariants and the gotchas about marks and Durable Object limits
2. `PRD.md` section 6.1, and the 2026-10-28 decisions
3. `docs/technical-architecture.md`, "Links"
4. `docs/reviews/2.5a-showing-links-review.md`

## What to do

1. **Run the checks:** `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`. Report exact results.
2. **Try to break the one-unit behaviour.** Add tests in `tests/unit/lib/wikilink-qa.test.ts`, using real TipTap and Yjs as `tests/unit/lib/wikilink-editing.test.ts` does. Explore:
   - two links next to each other, a link at the start or end of a line, a link that is the whole line
   - a link split by comment or suggestion marks
   - selections that partly cover a link, then typing, Backspace or cut
   - Enter at a link's edge
   - undo after deleting a link
   - remote edits (a second `Y.Doc`) that insert text inside a link while the cursor is next to it
   - the interaction with bullet keys (`app/lib/bullet-editing.ts`) on lines like `\t- [[link]]`
3. **Try to break display.**
   - Title changes while the cursor sits at a stale link's edge.
   - A title equal to the copy except for case.
   - Empty titles, a link whose copy is empty, and very long titles.
   - Several editors sharing the store (the feed): does one editor's request flood the route, and do destroyed editors leave listeners behind?
4. **The guard.**
   - Read `workers/app.ts` and `agents/document.ts`. Look for a document WebSocket path that bypasses the check: trailing slashes, encoded characters, query tricks like `?format=4&format=3`, or casing.
   - Check `clientUnderstandsFormat` edge cases.
   - Check that non-WebSocket requests and the workspace agent are unaffected.
   - Read PartySocket (`node_modules/partysocket`) and confirm that `useYjsEditor`'s `socket.close()` really cancels the reconnect it schedules before dispatching `close`.
5. **The route and the index.**
   - Validation, duplicate IDs, and exactly 100, 101 and 200 IDs through `pagesByIds`.
   - That journals not yet written are never reported as missing.
   - That no response reveals anything beyond titles of pages that exist.
6. **If you can run headless Chrome against `npm run dev`:**
   - Seed a stale link: create a page, rename it through `POST /api/rename`, and write a link to it from a format-4 Yjs client.
   - Check cursor drawing at both edges with `view.coordsAtPos`.
   - Check arrow keys, Shift+arrow, click and Alt+Enter.
   - Check IME-like input with `Input.imeSetComposition` at a link's edge.

## Rules

- Only add test files. If you need temporary changes to run something, revert them and leave no diff.
- If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)`, and add a comment explaining the bug.
- Do not lower coverage floors or weaken tests.
- Do not deploy or touch any Cloudflare account. Do not commit or push.

## Report format

Start with one line: the check results.

Then list findings, most severe first. For each:

- **Severity**: high (text lost or corrupted, a guard bypass, or repeated reconnects or wake-ups), medium, or low.
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**.
- **Suggested fix**.

Then "Not checked". If you find no real defects, say so plainly.
