# QA prompt: M2 chunk 2.1b, readable URLs

Paste everything below the line into a coding model that has access to this repository (for example Claude Code, Codex or Cursor), opened at the repo root.

---

You are doing independent quality assurance on a change made by another AI model. Your job is to find real defects, not to restate what the code does. Be skeptical: assume there are bugs until you have checked. This change includes the first schema migration of a live index, so look hard at upgrade safety, and at what a person following old links would see.

## The project

Mistlog is a Logseq-style notes app forked from Mist (Cloudflare Workers, Durable Objects, React Router 7, Yjs). Each page is a `DocumentAgent` Durable Object; a `WorkspaceAgent` holds a derived index. Pages have titles (`meta.title` in their Yjs document).

This change gives titled pages readable addresses:

- `/page/<slug>`, with `/docs/<id>` as the permanent address that redirects to it
- old slugs keep redirecting after a rename
- slugs are stored in the index, which migrates its schema from version 1 to 2

Read these first, in order:

1. `AGENTS.md`: repo rules, product invariants and gotchas, especially index migrations.
2. `PRD.md`: feature F2, open question 3, and the decision log entries dated 2026-10-24 and 2026-10-25.
3. `docs/technical-architecture.md`: the "Readable URLs" and "Workspace Index" sections.
4. `docs/reviews/2.1b-readable-urls-review.md`: the author's review guide, with slug rules, decisions and known limitations.

## What to do

1. **Run the checks** and report the exact results: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
2. **Check the requirements.**
   - Old links must keep working after renames.
   - `/docs/<id>` must always work, even with the index down.
   - The index must stay derivable apart from `registry` and `slugs`.
   - Migrations must be append-only and transactional.
   - Browsers must reach the index only through server routes.

   Flag any mismatch.
3. **Try to break it.** Add tests in new files: `tests/unit/agents/slugs-qa.test.ts` (use `memoryDb` from `tests/helpers/sqlite.ts`) and `tests/unit/routes/page-routes-qa.test.ts` (copy the mocking approach from `page-routes.test.ts`). Explore at least:
   - **Slug invariants under random operations.** Generate random sequences of renames across several pages, using titles that clash after slugifying. After each step check that:
     - each page has at most one current slug
     - each slug belongs to exactly one page
     - every slug a page ever had still resolves to some page
     - re-indexing without a title change never changes a slug

     Report any sequence that breaks one.
   - **Takeover and history:** A "Notes" → "Ideas", B "Notes", B → "Other", A → "Notes". Who holds what, and where does every old link go? Is anything surprising enough to report?
   - **Suffixes:** titles whose slug already ends in something like `-abcd`. Can page X's suffixed slug collide with page Y's plain slug, for example Y titled "C Dddd"? Pages whose IDs share a 4-character prefix.
   - **`slugify`:**
     - Unicode case folding (`İ`, `ß`, `Σ`/`ς`) and NFC versus NFD
     - zero-width and bidirectional control characters
     - emoji with combining marks
     - titles that slugify to the same string in different forms
     - lengths near 80 code points
     - does the cap ever produce a trailing `-` or an empty slug?
   - **Migration:**
     - an index with thousands of titled pages
     - titles that clash
     - an index created by 1.4 code with data in every table
     - a crash part-way (simulate with a trigger)
     - opening twice concurrently, with two constructors on the same database
     - a `schema_version` that is missing, not a number, or newer than the code
   - **Routes:**
     - encoded and double-encoded slugs (`%2F`, `%252F`)
     - slugs containing `/`, `..` or `%00`
     - a very long slug
     - an old slug whose page now has no slug
     - `/docs/<id>` when the index throws or returns odd data
     - redirect loops: can any combination of index states make `/page/a` redirect to `/page/a`, or `/docs/<id>` and `/page/<slug>` redirect to each other?
4. **Review the tests themselves.** Find assertions that would pass even if the behaviour broke. Mutation-test a few lines of `assignSlug`, `resolveSlug`, the migration loop and `page.$slug.tsx`, beyond those listed in the review guide. Run the tests, then put each one back.
5. **Check the design** against what comes next:
   - 2.1c journal pages at `/journal/YYYY-MM-DD`
   - 2.5 links and backlinks, which will build URLs with `pagePath`
   - 1.6 rebuilds through the registry
   - deleting pages (M5)
   - Logseq export (F15)

   Is the slug design likely to cause trouble for any of them?

## Rules

- Do not change production code in `app/`, `agents/`, `workers/` or `wrangler.jsonc`. Only add test files. If a test you write fails because of a real bug, keep it, mark it with `it.fails(...)` and add a comment explaining the bug, so the suite stays green.
- Do not lower coverage floors or weaken existing tests.
- Do not run `wrangler deploy`, `npm run deploy`, or anything against a Cloudflare account. Local `npm run dev` is fine.
- Do not commit or push. Leave changes in the working tree for a human to review.
- Do not report style preferences, or the known limitations in the review guide, unless you think one is more serious than the author claims. If so, say why.

## Report format

Start with one line: the check results (typecheck, lint, tests, coverage, build).

Then list findings, most severe first. For each:

- **Severity**: high (a broken or wrong link users will follow, a redirect loop, a failed or corrupting migration, or a page that cannot be reached), medium (a confusing redirect or URL in a case users will hit), or low (unlikely edge case, or a test gap).
- **Where**: `file:line`.
- **What**: one sentence.
- **Evidence**: steps or input, the expected outcome and the actual outcome, or the name of the failing test in your QA file.
- **Suggested fix**: one or two sentences.

Then a short section, "Tests that would not catch a regression", listing weak assertions you found.

End with "Not checked": anything you could not verify, and why. For example, the migration on the deployed index, or browser handling of percent-encoded Unicode URLs.

If you find no real defects, say so plainly. Do not invent findings to fill the report.
